# Design — C-03 auth-admin-shell

## Context

Ver `proposal.md` (Why + scope) y `specs/auth-admin-shell/spec.md` (contrato observable). Estado actual: C-01 archivado — `middleware.ts` raíz es STUB (denegar-todo → `/admin/login`), `/admin/login` es stub estático, `lib/supabase/{client,server,middleware}.ts` siguen el patrón oficial `@supabase/ssr` (`updateSession` con `getClaims`, `createClient` anon + cookies, `createServiceRoleClient` sin cookies), `.env.local` con keys live validadas. C-02 archivado — `perfiles (id UUID PK→auth.users, role CHECK admin|superadmin)` es LA única fuente de roles (DD-09; `user_metadata` prohibido), RLS probada live (INSERT anónimo ok, SELECT anónimo denegado, SELECT admin ok), bootstrap del primer admin manual por dashboard (sin credenciales en repo). Este change no toca DB.

## Goals / Non-Goals

**Goals:**

- Reemplazar el stub por guardia real de sesión + rol con el SDK oficial, sin cambiar el matcher (`/admin`, `/admin/:path*`) ni las rutas públicas.
- Login server-side con error genérico y a11y de formulario desde el día 1.
- Protección anti-abuso del login server-side desde el día 1 (rate limit + honeypot), con paridad de enfoque con C-04.
- Un único helper server-only de autorización que C-05/C-10 reutilizan sin copiar lógica.
- Shell admin mínima que no anticipe la tabla de leads (eso es C-05).

**Non-Goals:**

- Tabla de leads, filtros y paginación (C-05); formulario de captura y `/politicas` (C-04); gestión de usuarios/roles UI (solo bootstrap manual C-02; UI de usuarios es Instancia 2 si se pide).
- Recuperación de password, MFA, OAuth u otros providers (fuera de KB; change nuevo si se piden).
- Rate limit distribuido / Redis-Upstash (fuera de scope: el contador in-memory documenta el trade-off en Decisión 8; Redis/Upstash es change nuevo si el tráfico lo exige).
- Cambios de estilo global o footer completo (solo link discreto; footer definitivo en C-06/C-09).

## Decisions

1. **Middleware = sesión; layout = rol.** El middleware (`middleware.ts` raíz) solo verifica sesión vía `updateSession` + `getUser`: sin sesión → redirect a `/admin/login?next=<destino>`; con sesión en `/admin/login` → redirect a `next` interno o `/admin`; con sesión en resto de `/admin/*` → deja pasar. La verificación de rol vive en `app/admin/layout.tsx` (RSC server-only) vía helper `requireRole()`. Rationale: el middleware corre en edge en cada request — debe ser barato (una lectura de sesión) y no puede renderizar 403 con contexto; el layout decide autorización con query a `perfiles` una sola vez por render y responde 403 sin filtrar datos. Alternativa (rol también en middleware) descartada: duplica la query por request, complica el 403 (el middleware no renderiza páginas) y acopla edge a lógica de dominio.
2. **Login como Server Action autenticada como API route.** `app/admin/login/page.tsx` (RSC) renderiza el formulario (Client Component mínimo solo para UX: pending con `useFormStatus`/transición, sin secretos); la Action valida con `loginSchema` (zod, `lib/validaciones.ts`), llama `signInWithPassword` con el cliente servidor anon y ante fallo devuelve siempre el mismo mensaje genérico. Rationale: R1 (RSC + Action, cero queries Supabase desde Client Components) + regla vercel-react-best-practices ("authenticate server actions like API routes": re-validar input, no confiar en el cliente, redirigir solo a destinos internos). Alternativa (login directo con cliente browser) descartada: expone el flujo a manipulación del cliente y dificulta el mensaje genérico uniforme + auditoría server.
3. **Helper `lib/auth.ts` server-only, rol por query simple.** `getRole()` → `supabase.auth.getUser()` + `SELECT role FROM perfiles WHERE id = <uid> LIMIT 1` (single row, sin `EXISTS` innecesario a nivel app; el patrón `(select auth.uid())` ya vive en las policies RLS de C-02). `requireRole(['admin','superadmin'])` lanza/retorna 403 si falta rol. Módulo marcado `import 'server-only'` y sin importar `service_role` (anon + RLS alcanza: la policy `perfiles_select_own` permite leer la propia fila). Rationale: una sola fuente de verdad (DD-09), sin staleness de JWT, reutilizable por C-05/C-10. Alternativas descartadas: leer `user_metadata.role` (inseguro — editable por el usuario, prohibido por skill `supabase` y spec C-02); usar `service_role` para leer roles (innecesario, expande superficie; R3).
4. **Logout en dos caras con una sola verdad server.** Botón en shell admin invoca Server Action `signOut` (cliente servidor → `supabase.auth.signOut()`, limpia cookies) y luego el cliente ejecuta `router.replace('/admin/login')` + `router.refresh()`; el cliente browser también invalida su estado local. Rationale: cubre "cierra sesión en cliente y servidor" del roadmap sin dejar cookies huérfanas ni estado fantasma; el back-button no re-expone contenido porque la RSC re-verifica sesión en cada navegación.
5. **Cookies delegadas al SDK, cero manejo manual.** `httpOnly`/`secure`/refresh provienen de `createServerClient` + `updateSession` ya existentes (C-01); este change solo los cablea en `middleware.ts`. No se setean cookies a mano ni se copian tokens a logs (RN-AU-04). Rationale: el helper C-01 sigue el patrón oficial verificado; manipular cookies a mano es la causa típica de deslogueos aleatorios (advertencia oficial citada en el propio archivo).
6. **Formulario login con shadcn accesible, sin inventar estilos.** Componer `FieldGroup + Field` (con `data-invalid` + `aria-invalid`), `Alert` con `role="alert"` para el error genérico, `Button` con spinner + `disabled` en pending (no existe `isPending`). Rationale: cumple el checklist WCAG de formularios (KB `11`) con componentes ya disponibles; evita CSS ad-hoc que rompa contraste/foco.
7. **`loginSchema` nuevo en `lib/validaciones.ts`, `leadSchema` intacto.** `loginSchema = { email: trim+lowercase+email, password: min(1) }` — password solo presencia (la autoridad es Supabase Auth; no imponer longitud acá evita filtrar política de credenciales). Rationale: R2 (schemas compartidos); el login no reutiliza `leadSchema` (dominios distintos).
8. **Anti-abuso del login: rate limit in-memory por IP+email + honeypot con error byte-idéntico (paridad C-04).** La Server Action de login ejecuta SIEMPRE en servidor, en este orden: (a) chequeo honeypot — campo invisible (p. ej. `website`, `tabIndex={-1}`, `autoComplete="off"`, `aria-hidden="true"`, oculto off-screen sin `display:none` para no delatarse, excluido de tab order y de lectores); si llega no-vacío → retorno inmediato del mensaje genérico BYTE-IDÉNTICO — copia exacta `"Credenciales inválidas o cuenta no encontrada."` — sin llamar a Supabase Auth, sin log diferencial y SIN incrementar ni resetear los contadores de rate limit (el honeypot no contamina contadores: un atacante no puede envenenar/limpiar contadores ajenos con el honeypot); (b) chequeo rate limit — contador en `lib/rate-limit.ts` (Map in-memory con ventana deslizante/expiración: clave dual por IP normalizada + por email normalizado, contadores SOLO en servidor; umbral pineado: 5 intentos fallidos por ventana de 10 minutos; backoff progresivo pineado: 5.º fallo → bloqueo 2 min, 6.º → bloqueo 10 min, 7.º en adelante → bloqueo 30 min); si excedido → NO se llama a Supabase Auth y se devuelve el MISMO mensaje genérico byte-idéntico `"Credenciales inválidas o cuenta no encontrada."` (cero fuga de información: inválidas, honeypot y bloqueo son indistinguibles por cuerpo de respuesta; la única diferencia aceptada es el skip inevitable de la llamada Auth en el path honeypot, sin diferencia de copy ni de anuncio). El conteo se incrementa solo ante intento real con fallo de Auth (no ante honeypot). El freno nativo de Supabase Auth sigue como segunda capa. Rationale: R1 (enforcement solo servidor, cero confianza en el cliente) + RN-AU genérico (05) + paridad con el enfoque honeypot+rate-limit ya previsto para `registrarLead` (C-04 futuro; no se tocan artefactos C-04). Alternativas descartadas: enforcement solo-cliente (bypass trivial); CAPTCHA (fricción + dependencia externa, desproporcionado para login interno de bajo tráfico); Redis/Upstash ahora (costo/complejidad injustificados; el in-memory es dependency-light y funciona en serverless con degradación conocida, ver trade-off).

## Risks / Trade-offs

- [Riesgo] Loop de redirección si `/admin/login` exige sesión → Mitigación: el middleware deja pasar `/admin/login` siempre; la RSC de login redirige solo si hay sesión + rol (o sesión válida según spec), nunca si no hay sesión; test explícito de no-loop.
- [Riesgo] 403 vs redirect confuso (¿rol insuficiente redirige a login?) → Mitigación: autenticado-sin-rol = 403 (spec), no-autenticado = redirect; el aviso interno va a log server con `uid` (sin email ni tokens), nunca al cliente.
- [Riesgo] `getUser` vs `getClaims` en middleware (staleness/costo) → Mitigación: `updateSession` mantiene `getClaims` para el refresh (patrón oficial); la verificación de identidad para redirect usa `getUser()` (verdad server, no claims cacheados); la query de rol va en el layout, no en cada request edge.
- [Riesgo] `forbidden()`/`unauthorized()` cambian entre versiones de Next → Mitigación: implementar el 403 con el mecanismo vigente de Next 15 verificado en implementación (`forbidden()` si existe, si no página `403` dedicada + `status 403`); no asumir API sin verificar contra docs del repo/instalado.
- [Trade-off] Rate limit in-memory (no Redis) → aceptado y documentado: en serverless Vercel el contador vive por instancia/régimen (cold start o escalado lo reinicia, un atacante distribuido por muchas IPs lo diluye); aceptable para login interno de bajo tráfico + freno nativo de Supabase Auth como segunda capa. Si el abuso escala, el reemplazo es `lib/rate-limit.ts` por backend persistente (Upstash/Redis) sin cambiar la Server Action (change nuevo, fuera de scope).
- [Riesgo] Honeypot delata o rompe a11y (lectores lo anuncian, autofill lo completa, timing filtra la causa) → Mitigación: `aria-hidden` + fuera de tab order + off-screen (no `display:none`), `autoComplete="off"`, nombre de campo señuelo no-autocompletable; el rechazo honeypot devuelve mensaje byte-idéntico `"Credenciales inválidas o cuenta no encontrada."` con el mismo `role="alert"` y no llama a Auth (cero diferencia de copy/anuncio; diferencia de timing por skip de Auth aceptada como inevitable, con no-log diferencial).
- [Trade-off] Shell admin mínima con placeholder → aceptado: evita anticipar C-05; el placeholder indica explícitamente "listado de leads en C-05" para no confundir QA.

## Migration Plan

1. Implementación edita `middleware.ts`, `app/admin/login/page.tsx` (+ Client Component de formulario con honeypot invisible), crea `app/admin/layout.tsx`, `app/admin/page.tsx` placeholder, `lib/auth.ts`, `lib/rate-limit.ts` (contador in-memory clave dual IP+email: 5 fallidos/10 min, backoff 2/10/30 min en 5.º/6.º/7.º+, contadores solo servidor, honeypot no contamina contadores), extiende `lib/validaciones.ts` con `loginSchema`, agrega link en `app/layout.tsx` footer. Cero migraciones.
2. Verificación: `tsc + lint + build` verdes; tests/flujos manuales (login ok, credenciales inválidas → copia exacta, honeypot→misma copia exacta byte-idéntica sin sesión ni llamada Auth ni toque de contadores, rate limit→misma copia exacta byte-idéntica sin filtrar validez con checks escalonados 5.º→2 min / 6.º→10 min / 7.º→30 min, aserción byte-idéntica entre los 3 casos, `next=` preservado, refresh/expirada, anon→redirect, sin-rol→403, logout→redirect, footer link); Lighthouse/a11y del login (contraste, foco, `role="alert"`, honeypot invisible para AT).
3. Rollback: revert del change (el stub C-01 queda en git); sin datos que migrar ni revertir.
4. Post-merge: C-05 consume `requireRole()` + shell sin modificar auth; C-04 corre en secuencia (orden usuario) sin tocar `/admin`.
